# dydo 3.0 Linear-Native Work-Model Assimilation

This brief captures what Project 2 changed, what its dogfood exposed, and what remains deliberately
deferred. Durable lessons live here; volatile execution state remains canonical in Linear.

## Outcome

Project 2 replaced dydo's file-backed live-work vocabulary and machinery with a clear ownership
boundary: Linear owns live Initiatives, Projects, Issues, optional Milestones/Cycles, dependencies,
assignment, review state, and updates; Git owns durable knowledge, reviewed Project plans, immutable
delivery proof, audits, and assimilation. FutureFeature remains an unscheduled repo-native idea until a
human promotes it once. No Linear runtime integration or repository mirror was built.

Independent document review and the strict integrated Project audit both returned **PASS with zero
findings** on the complete five-path candidate based at exact amended master `1032d5d1…`. The immutable
evidence commit and its canonical completion state remain linked from Linear after push rather than
being recursively copied into the commit that names them.

## Adopted improvements

### Creation-time visible-task callbacks

Visible Codex task delegation initially lacked a reliable completion path back to its coordinator. The
accepted improvement landed in
[`818f87a6a58c7dcffe342978124288cab35e423b`](https://github.com/bodnarbalazs/dydo/commit/818f87a6a58c7dcffe342978124288cab35e423b):
the initial delegation must name the coordinator task/thread ID and require a blocked-or-completed
callback carrying status, blocker, branch, exact commit, review verdict, and gate evidence. The
coordinator registers and waits on visible tasks; native subagents retain their native return path;
Linear remains canonical for work state. DYD-16 dogfooded this contract by registering coordinator
`01a04298-1bc6-7b90-a387-71e33efc680a` before work and reserving proactive blocker/completion callbacks.

### Exact evidence-only retired-PM predicate

The initial zero-hit scan could not distinguish a retired consumer from an assertion proving that the
retired path is absent. The reviewed amendment
[`8d703ab93c1c87bfe0d01df562b8186b15b7b405`](https://github.com/bodnarbalazs/dydo/commit/8d703ab93c1c87bfe0d01df562b8186b15b7b405)
replaced broad suppression with a closed allow-set of exactly five normalized-path plus
full-trimmed-source tuples: three parser fixture strings and two negative
`TemplateGeneratorTests` assertions. Each tuple must occur exactly once; missing, duplicate,
unparseable, or additional matches fail. The integrated run proved `raw=5; allowed=5; unexpected=0`,
while separate predicates proved the retained historical fixture corpus has zero live consumers and
zero active content includes.

### Reviewed intent and integrated acceptance

Issue-level work now begins from one autonomous-ready Linear Issue or a linked reviewed Git Project plan.
Each implementation Issue receives an independent review, and coordinated work receives a strict
Project-level audit against the linked plan after serial integration. Assimilation is an acceptance
surface, not a session afterthought. The merged methodology, workflows, templates, generated skills, and
active docs agree on this contract.

### Token-aware generated summaries

Generated navigation is an acceptance surface, not harmless formatting. DYD-16's byte-parity proof
exposed that a generator can be deterministic and still be wrong: raw first-period extraction broke
dotted versions, `.NET`, and Markdown code tokens. The adopted product behavior protects Markdig
`CodeInline` spans, recognizes terminal punctuation only at a whitespace/end boundary, preserves raw
Markdown, and truncates at a safe token boundary within 150 characters. The fix is pinned by real
regressions and deliberately avoids the Sync/Projection compatibility code scheduled for removal.

## Observed dogfooding friction

- The global PATH command was `dydo 2.2.9+a4a16ed…`, while the integrated Release build was
  `dydo 2.2.9+5cceda39…`. Bare `dydo sync` exited 0 but regenerated two Claude workflows back to the
  retired 2.x Campaign/Sprint contract. Those out-of-scope diagnostic writes were restored exactly;
  the source-built command then produced zero semantic diff. Acceptance commands must therefore pin the
  exact built revision when global and repository binaries can diverge.
- The installed PowerShell profile invokes `dydo completions powershell | Invoke-Expression`. The stale
  global binary repeatedly emitted a malformed completion script (`Missing closing '}'`), adding noise
  to every profiled shell. This is product/tool-installation friction, not agent-harness behavior, so the
  self-improvement methodology correctly authorized no harness or policy edit inside DYD-16.
- Sandboxed first attempts could not read the user NuGet config, Python runtime, or owner-only Git
  worktree metadata. Authorized reruns succeeded. No repository workaround or broadened permission was
  encoded in product files.
- Manifest verification refreshes receipt provenance in its working copy. DYD-16 treated those
  command-produced changes as non-owned evidence noise and restored the exact merged artifacts instead
  of absorbing Project-3 corpus edits.

## Deferred follow-ups

- Project 3 alone may ratify and apply the disposition manifest, normalize retained FutureFeatures,
  remove the frozen legacy corpus, and introduce the strict FutureFeature content fixtures.
- Project 5 alone may remove the stopped Notion adapter, generic sync/watchdog/token/schema surfaces,
  local rollback stores, and their tests after the required dogfood acceptance.
- Updating the globally installed dydo binary and repairing/reinstalling its PowerShell completion hook
  need a separately authorized product/tooling Issue. DYD-16 records the evidence but creates no Issue
  and changes no user profile.
- Repository↔Linear synchronization, a Linear client/cache/mirror, and status projection remain
  explicitly rejected, not postponed implementation work.
- Project completion, Project-3 Issue creation, and any mutation of DYD-12 through DYD-15 remain with the
  authorized coordinator/human flow.
