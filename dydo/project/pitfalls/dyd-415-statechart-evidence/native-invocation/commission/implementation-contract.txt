## Public request, approval and resume protocol v1

Public operation: `dydo statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]`. Preserve existing default config/output, caller cwd, relative paths, Unicode/spaced argv and original override meanings. Normalize paths once for stored requests; do not chdir into the asset cache and reinterpret inputs. `doctor` is optional/offline discovery; `setup` is optional and uses the same installer, not a required two-command journey.

1. **Capture/resolve.** Parse arguments, validate top-level inputs/output contract and installed payload. Record original argv, absolute caller cwd and resolved model/config/view/out, original explicit overrides, selected RID, release/payload/lock/protocol identities. Do not store the full environment. Retain model/config/view top-level content hashes to detect edits across approval delay; do not copy models into a new cwd and break imports. Do not claim to freeze arbitrary view imports or the full TLA module closure.
2. **Ready.** Reuse verified compatible dependencies; no network/consent/install. Enter the owned checking lifetime and run the same request. Readiness means required JS, Java, TLC and renderer can run/import under the selected paths, not a marker's mere presence. Full code checking is not run just for discovery on every invocation; use bounded identity/version/import checks, cache receipts bound to selected file identities, and real setup readiness proof when publishing a new receipt.
3. **Missing.** Print the concrete missing dependencies, selected versions/hashes/URLs, task/user-scoped destinations and download/extraction bounds. Atomically create an owned pending request under the chosen state root, plus a structured JSON event: `schema:1`, `state:"approval-required"`, `requestId`, request path/digest, lock/payload identities, missing assets, destinations, original resolved inputs, and exact install-and-continue argv. Exit **3**, not chart verdict0/1. Use `dydo statechart resume --request ABSOLUTE_REQUEST_JSON` as the proposed install-capable continuation command. It is a capability operation, not an `--approved` assertion.
4. **Normal host authorization.** An ordinary CLI has no T3/Codex permission API and cannot authenticate a flag as user consent. It must not silently install from the initial missing path, fabricate host transport, read internal host approval files, alter DYD-433 mode or ask agents to hand-run dependency diagnosis. The installed skill handles the structured event by invoking the exact continuation command through the host's normal command/installation approval mechanism (sandbox escalation where supported), describing the locked plan. The tool host/user policy grants or denies that tool action. Local JSON, a nonce or a receipt is NOT evidence of host approval. A host with a real documented in-process approval callback could keep the original invocation alive and continue, but no such integration is assumed or commissioned here.
5. **Install/verify/continue.** Once the host authorizes execution of that continuation operation, its process reloads/validates the request and immutable identities, recomputes permitted destinations, acquires the managed dependency lock, rechecks readiness (another invocation may already have installed), downloads only missing locked assets, verifies archive hashes before extraction, verifies readiness, publishes receipt atomically, then executes the saved chart request in that process with the new ownership lifetime. No separate `setup` command or model resubmission. No request-file `approved:true`, secret consent token or self-authorizing flag. If dependencies became ready while waiting, continuation skips all installation.
6. **Unavailable/denied.** No child provisioning action starts. Keep request and show the concrete host denial/unavailable route, original inputs and retry command; no success. The skill may report the host denial but cannot synthesize a CLI exit that was never observed. If the host cannot authorize the continuation, return the gap. A CLI-local failure uses2; chart0/1 remain reserved for actual checker outcomes. Signals preserve130/143 where supported.
7. **Failure/cancel/retry.** Download/hash/extraction/readiness errors and cancellation preserve the pending request and failure reason, publish no ready receipt, and clean only this attempt's owned staging after child teardown. Ready previously published components survive. Retry uses the same resume request through normal host rules; validation rejects changed source paths/top-level hashes, new lock/payload/protocol or changed plan destinations and asks the capability to prepare a fresh plan. Do not re-consent ready dependencies. Completed requests get a completion receipt binding actual verdict/output identities; repeated resume returns recorded status rather than unexpectedly rerunning output writes. A changed/missing completed output is a specific stale-result failure, not a fake replay success.

Thus one invocation continues in-process when already ready; the supported noninteractive host path needs one normal approval/resume tool action when missing. That is the honest limit of "ideally same invocation" without a host permission API. No further architecture approval is requested.

## Lifetime protocol and chosen topology

Use statechart-only internal control messages, version1 with a random per-run channel identity and current-user-only access. Separate control from model/view stdout and user input. Validate exact message order and fields. Schema mismatch, duplicate/out-of-order/oversize frame, invalid path/identity or EOF before its gate fail closed. A nonce correlates channels; it is neither host approval nor security against a same-privilege malicious process. All child creation hidden on Windows, including Java discovery, managed readiness, janitor, JS/Java, npm shim and tests. Do not set a finally-only process-tree kill as ownership.

Windows selected topology: public native dydo **N** is outside a fresh non-breakaway kill-on-close job; **C**, the TS CLI, and worker/Java descendants are inside it. Detached independent cleanup **J** is outside that checking job. N holds the only job handle; J must never inherit/duplicate it (that would keep last-close from killing members when N dies). Reuse reviewed embedded Job Object implementation where valid; use compile-time/AOT interop and real Win32 error handling. Its old separately compiled proof is not proof of new production AOT code.

Windows order:

1. Resolve dependencies and payload before checking processes. Create job/kill-on-close and completion port. Start J detached/hidden with only its intended lifetime/control/notification handles; explicit handle inheritance list prevents leaking N's job handle or pipe writers into children. J acknowledges protocol/ready before any checking scratch or worker can exist.
2. N starts a minimal TS bootstrap C with **no worker/view/Java before GO**. Assign C to the job while still gated, connect lifecycle channel and confirm assignment. EOF/native death before GO exits without checking descendants. Assignment failure is a concrete Win32 failure, not a fallback launch.
3. C validates output using existing destination rules, requests fresh stage/TEMP reservations. J journals the exact reserved names, creates exclusively, records directory/file identities and acknowledges registration before worker creation/release. A path created but not identity-registered during an interrupted handshake is retained as ambiguous, never recursively adopted/deleted. Before registration no worker/Java may run. This closes the source-based janitor early-rejection window.
4. C starts worker inherited into the same job; worker ready/go remains and extends to all platforms. GO requires native ownership AND registered stage/TEMP AND live cleanup channel. Do not import the user view or start SANY/TLC before it. C owns existing output validation and final stage/done publication; J never deletes output.
5. On normal completion C publishes only verdict0/1 complete output under existing nonempty/concurrent-arrival rules and exits. N stops remaining job members. J waits for confirmed job drain before deleting only registered still-matching stage/TEMP; N reports final status after cleanup acknowledgment. Keep TLC verdict separate from setup/lifetime failure. On parent death J observes EOF independently and waits for termination/drain before cleanup.
6. J can consume a duplicated **completion-port** handle for job notifications without owning the job handle. Job ACTIVE_PROCESS_ZERO is an event, not a guaranteed cleanup oracle: missing/ambiguous notification or teardown deadline retains scratch with a durable error instead of deleting possibly live files.
