## Example

You wanted testing to become cheaper without losing protection against breakage elsewhere. Three improvements are now merged: agents have clearer instructions to run relevant tests, test evidence has a safer retention recipe, and one flaky test has a realistic deadline. The automatic extra-test system and its Linux rollout still need work; the whole project is not finished.

The useful changes are:

* **Run the relevant tests while building.** Agents now normally run the affected feature's fast tests, rather than whole suites after every edit. Expensive tests for that feature belong at final gates; whole suites belong in periodic CI or an explicit request from you. This delivers the policy you approved; it is not a measured speed-up claim.
* **Keep proof files long enough to inspect them.** Some test runs lost their evidence when concurrent runs rotated shared temporary folders. The new recipe gives each evidence-producing run its own temporary location and collects the proof before cleanup. It changes the instructions, not pytest's global retention.
* **Stop mistaking a slow error-reporting test for a timeout.** A test meant to prove that a child process reports an error had only half a second to finish. It now gets ten seconds. The separate test that deliberately times out still has its half-second limit, and the assertions remain intact.

The largest unfinished piece is **Ripple**, which chooses a small extra set of tests from past failures to catch damage outside the feature being changed. One fix corrects misleading incident counts: if one browser test fails and twenty later tests cannot run because of it, those twenty should not turn one failure into a broad incident. You already approved that behavior.

That fix is held. Two verification runs failed, and the remote pull request still conflicts with newer code. The environment investigation could not establish that Git Bash's temporary-directory mapping could be inspected without touching another task's files. The proposed check was rejected in review; a third run was not started. That does not prove another task caused the failure. I own preparing a concrete, compliant inspection method with the responsible captain, or keeping the hold if none exists. Once that prerequisite is cleared, the captain owns reconciling the pull request with current code, passing verification and obtaining fresh review before offering it for merge. A vague request for you to “change the evidence boundary” would not give you anything useful to approve.

A separate fix prevents a hung setup-wizard test from leaving child processes running. Its Windows proof passed. Linux proof never began: container setup stopped at a check of process resource isolation, and the retained evidence does not establish the cause. Its captain and I own preparing a limited diagnosis of which Linux process-isolation controls are available and whether they enforce the required resource limits. That diagnosis needs its own allocation; no further test run is authorized by this catch-up. It still needs Linux proof and fresh whole-change review.

The Linux test machine also needs its installed updater brought forward. The last inspection found a real job still running, an old separately installed updater, and the new Ripple-list retrieval code absent from the deployed release. Those are historical observations, not a claim about its health right now. I own checking current readiness and coordinating with the host owner. We will not stop a healthy job merely to create an installation window.

**One policy decision is ready for you:** what should a test command report when the routine checks pass, but proof reserved for a separate expensive run is still missing?

Here, coverage means evidence that tests exercised the code being assessed. Routine checks can pass for the code they cover while 45 source-code entries on the project's explicit list still await their designated expensive checks. Today that missing evidence returns the same failure exit code as broken code. I recommend a **distinct “evidence pending” exit code**, while keeping the printed result PENDING, never PASS. It lets scripts tell “not proved yet” from “tests failed”; it does not authorize merging without required proof.

The alternatives are to keep today's failure code and have callers interpret the text; return success, which would blur missing proof with complete proof and requires changing the governing policy; or routinely run the expensive checks, which adds cost. Reusing evidence from other commits or machines would be a separate design, not a shortcut already approved. This choice changes how every agent and caller interprets the gate, and the recorded ruling reserves it for you. Without an answer, the current failure code stays and this policy change waits. The other work above can continue within its existing limits.

There is also a **human installation step later**, not an unexplained scheduling request now. The existing contract requires you to run the updater wizard. Once I have checked readiness, I will bring the tested command and a concrete idle window. Proceeding then installs the reviewed updater and lets us verify its version and health, then check that agents can retrieve the published list of extra tests from the Linux host; deferring preserves running work but leaves live acceptance open. I recommend proceeding when genuinely idle. I cannot replace the explicitly human-run installation with an agent action.

One optional policy question can stay parked: if one shared test fixture breaks and prevents more than twenty tests from running, should that still count as a broad incident? I recommend keeping the current behavior because the shared foundation is broken. Counting it once for the Node and Vitest runners would add a new grouping rule; including Python would also require additional failure evidence. This differs from later browser tests merely being skipped behind one failed test. Changing the definition is your policy choice, but it blocks nothing and needs no answer to retain today's behavior.

You do not need to confirm the mode flag: the subsequent read-only check returned **overnight off**. I also own reconciling stale board summaries and the unfinished post-merge records. The optional proposal to split test groups stays deferred until its owner updates it against the policy you already approved. None of those is another decision for you.
